# Agent 工具调用的幂等性与重试设计

## 1. 问题定位

LLM 输出是非确定性的，工具调用可能超时。当框架决定「重试一次工具调用」时，必须回答三个不同层次的问题：

1. **这次调用有没有副作用？** —— 决定能不能重试
2. **如果重发了，怎么保证只生效一次？** —— 决定重试的实现方式
3. **超时之后，结果到底是成功还是失败？** —— 决定重试之前要不要先做别的动作

很多方案只回答了第 2 个问题（加个去重表），结果在超时场景下照样重复下单。真正完整的答案需要三个一起回答。

核心判断：**重试策略本身不能解决幂等性问题**。重试只负责「再发一次」，它对副作用没有任何约束力。约束力来自三个独立机制：

- 工具的**语义声明**：告诉框架这个操作能不能安全重发
- 调用链上传递的**幂等键** + 下游的**去重账本**：保证同一个逻辑请求只生效一次
- 超时后的**状态查询**：明确「结果未知」这个状态，并给它一条出路

---

## 2. 先分类失败，再谈重试

把「工具调用失败」当成一个整体来讨论，是设计事故的起点。实际上它至少分三类，而重试的安全性完全不同。

### 2.1 三类失败

**第一类：请求没有到达服务端。** 连接被拒、DNS 解析失败、连接超时。服务端从未收到请求，确定没有副作用，重发是安全的。

**第二类：服务端明确拒绝了请求。** 参数校验失败（400）、鉴权失败（401）、资源不存在（404）。服务端收到并处理了，但没有执行任何业务逻辑，只是拒绝。这类失败重发没有意义——不修改参数，重发一百次还是同样的拒绝。其中 429 和 503 是例外：它们是「服务端暂时无法处理」，业务逻辑同样没有执行，重发是安全的。

**第三类：服务端可能已经执行，但客户端没拿到结果。** 这是最麻烦的一类，包括请求超时、连接中断、502/504 网关超时。

### 2.2 第三类才是幂等性问题的主战场

以一个下单接口为例：

```
客户端                服务端
  │                     │
  ├─── 创建订单 ────────▶│
  │                     ├─ 校验库存
  │                     ├─ 扣减库存        ← 副作用在这里发生
  │                     ├─ 写入订单表
  │                     ├─ 发送消息
  │                     └─ 准备返回响应
  │                     │
  │◀── 等待中...         │
  │                     │
  ✖ 超时（5s）           │  ← 响应可能只是慢了，业务其实成功了
  │                     │
  └─ 客户端认为「失败」   │
```

问题在于：**超时是客户端视角的结论，不是服务端的实际状态**。超时的那一刻，业务可能成功、可能失败、可能正在处理中。如果框架把超时等同于失败并重试，就是第二笔订单。

所以第一条设计原则是：

> 超时不是失败，超时是「结果未知」。对写操作，结果未知时只能去查，不能重发。

### 2.3 为什么 LLM 调用可以放心重试

同样用这套分类看 LLM 调用，结论完全不同：

| | LLM 调用 | 下单接口 |
|---|---|---|
| 副作用 | 无（相同输入产生相同输出） | 有（改库存、写订单、发消息） |
| 重复执行的成本 | 多花一次 token 费用 | 重复发货、重复扣款 |
| 失败后的默认动作 | 直接重试 | 必须先确认状态 |

LLM 调用是无副作用的纯函数调用，重试的代价有明确上界（token 费用）。所以在 LLM 客户端层面做自动重试是合理的：网络错误、429、5xx 重试，401/400 这类明确的客户端错误不重试。

**这个区别是整道题的分界线**：同一个重试逻辑，放在 LLM 客户端上是对的，放在工具调用上可能就是资损。

## 3. 让框架感知工具的语义

要决定「能不能自动重试」，框架必须知道工具的语义，不能靠工具名猜。

### 3.1 用一组语义元数据，而不是一个布尔值

只声明「是否幂等」是不够的，因为它回答不了最关键的问题：**超时之后该怎么办**。一个幂等写的接口可以带键重试，一个非幂等写的接口则必须先查状态——这两者「是否幂等」的答案可能都是「否」，但处置方式完全不同。

所以需要三个正交维度：

```java
public enum Effect {
    /** 只读，不改变任何状态 */
    READ_ONLY,
    /** 幂等写：重复执行结果相同（覆盖写、置位、删除不存在的记录） */
    IDEMPOTENT_WRITE,
    /** 非幂等写：重复执行产生新效果（下单、转账、发消息、追加记录） */
    NON_IDEMPOTENT_WRITE
}

public enum UnknownOutcomePolicy {
    /** 放弃重试，把「结果未知」直接上报 */
    FAIL_FAST,
    /** 使用同一个幂等键重发 */
    RETRY_WITH_KEY,
    /** 先按幂等键查询状态，再决定重发还是直接返回 */
    RECONCILE_FIRST
}

public record ToolPolicy(
        Effect effect,
        Duration timeout,
        UnknownOutcomePolicy onUnknown,
        boolean autoRetry
) {
    /** 默认按最保守的方式处理：忘记声明的工具不会被自动重试 */
    public static final ToolPolicy CONSERVATIVE =
            new ToolPolicy(Effect.NON_IDEMPOTENT_WRITE, Duration.ofSeconds(5),
                           UnknownOutcomePolicy.RECONCILE_FIRST, false);
}

public interface Tool {
    String name();
    String description();
    ObjectNode parametersSchema();

    default ToolPolicy policy() {
        return ToolPolicy.CONSERVATIVE;
    }

    ToolResult execute(ObjectNode args, ToolContext ctx) throws Exception;
}
```

默认值取最保守的一种，这样「忘记声明」不会变成「被自动重试」。

### 3.2 语义如何驱动框架行为

| effect | 可并行 | 可自动重试 | 超时后的处置 |
|---|---|---|---|
| READ_ONLY | 是 | 是，重试上限内 | 直接重试 |
| IDEMPOTENT_WRITE | 不建议 | 是，复用同一幂等键 | 带键重试，下游保证只生效一次 |
| NON_IDEMPOTENT_WRITE | 否，必须串行 | 否，绝不自动重试 | 先查状态；查不到就返回不确定 |

框架不需要理解业务语义，只需要按这三类执行不同的策略。这张表是整个设计的决策中枢。

### 3.3 一个重要边界：写工具不应并行

READ_ONLY 的工具可以并行执行以降低延迟，但写工具并行会引入额外的竞态：

- 同一资源的两个写操作并发，可能互相覆盖（丢失更新）
- 失败时的回滚边界变得不清晰

所以写工具应该串行执行，或者对同一资源加互斥。这是幂等键之外的额外保护。

## 4. 幂等键：让下游能够识别重复请求

语义声明解决了「能不能重试」，幂等键解决「重试了怎么不出事」。

### 4.1 幂等键的来源

不需要发明新的标识符。OpenAI 的 function calling 协议本身就给每次调用分配了唯一 id：

```json
{
  "role": "assistant",
  "tool_calls": [{
    "id": "call_00_m5DlyHgCNWbWY7WnBSDA6703",
    "type": "function",
    "function": {
      "name": "create_order",
      "arguments": "{\"sku\":\"A001\",\"qty\":2}"
    }
  }]
}
```

这个 `id` 就是天然的幂等键：它在「模型决定调用」的那一刻生成，同一次调用在整条链路上保持不变。

框架只需要把它继续往下传，直到真正产生副作用的地方：

```
模型输出 tool_calls[].id
        │
        ▼
框架：解析调用，把 id 保存到调用上下文
        │
        ▼
工具：从上下文取出 id，作为 Idempotency-Key 传给下游
        │
        ▼
下游服务：用这个 key 做去重
```

### 4.2 关键约束：重试必须复用同一个键

这是最容易出错的地方：

| 做法 | 结果 |
|---|---|
| 重试时复用同一个 id | 下游识别为同一次请求，正确去重 |
| 重试时重新生成 id | 下游看到两个不同的 key，当作两笔业务，重复执行 |

所以幂等键必须在「调用被创建」时生成一次，之后所有的重试都复用它。绝不能写在 HTTP 客户端或者工具实现里「每次请求生成一个新的」——那样重试保护立刻失效。

如果幂等键来自框架外部（比如模型给的 id 可能缺失），需要有一个稳定的补位策略：在调用记录创建时生成并持久化，而不是在发送时临时生成。

### 4.3 下游的去重账本

幂等键本身不提供任何保证，必须有一张去重表来实现「只生效一次」：

```sql
CREATE TABLE idempotency_record (
    idempotency_key VARCHAR(64) PRIMARY KEY,
    request_hash    CHAR(64)     NOT NULL,
    status          VARCHAR(16)  NOT NULL,   -- PROCESSING / SUCCEEDED / FAILED
    response_body   TEXT,
    created_at      TIMESTAMP    NOT NULL,
    updated_at      TIMESTAMP    NOT NULL
);
```

处理流程：

```python
def handle_with_idempotency(key, request, biz_handler):
    request_hash = sha256(canonical_json(request))

    # 1) 抢占：依赖主键唯一约束，而不是「先查再插」
    inserted = insert_ignore(
        "idempotency_record",
        key=key, request_hash=request_hash, status='PROCESSING')

    if not inserted:
        # 2) 这个 key 来过
        record = select_by_key(key)

        if record.request_hash != request_hash:
            # 同一个 key 配不同的请求体，属于上游 bug，必须显式报错
            raise Conflict("idempotency key reused with different payload")

        if record.status == 'SUCCEEDED':
            return record.response_body          # 直接返回上次结果
        if record.status == 'PROCESSING':
            raise RetryLater("previous attempt still in progress")
        if record.status == 'FAILED':
            # 是否允许重试由业务决定，通常需要重新抢占
            ...

    # 3) 执行业务
    result = biz_handler(request)

    # 4) 落库
    update(key, status='SUCCEEDED', response_body=result)
    return result
```

几个必须做对的细节：

**用唯一约束抢占，不要先查再插。** 先查再插在并发下有竞态：两个请求可能同时查到「不存在」，然后都去执行。数据库的主键唯一约束是原子的，用它来裁决。

**校验请求体摘要。** 如果同一个 key 配了不同的请求体，说明上游有 bug。这时必须报错，而不是静默执行——静默执行会掩盖问题，让幂等语义变得不可信。

**缓存响应体。** 只做去重不缓存响应，重试虽然不会重复执行，但调用方拿不到正确结果。

**处理 PROCESSING 卡死。** 如果进程在执行业务时崩溃，记录会永远停在 PROCESSING。需要超时回收机制，或者用业务侧的唯一约束兜底（比如订单表对业务单号建唯一索引），让去重账本只作为快速路径。

## 5. 超时之后：先确认状态，再决定动作

有了语义声明和幂等键，还剩最后一个问题：超时返回错误之后，框架应该做什么。

### 5.1 三种处置策略

```
工具超时，结果未知
    │
    ├─ FAIL_FAST：放弃重试，把「结果未知」上报给调用方
    │   适用：只读操作、幂等且成本低的写操作
    │   缺点：用户体验差（「我不确定有没有成功」）
    │
    ├─ RETRY_WITH_KEY：用同一个幂等键重发
    │   适用：IDEMPOTENT_WRITE，或下游已实现去重账本
    │   前提：下游的去重必须真的生效，否则等同于重复执行
    │
    └─ RECONCILE_FIRST：先按幂等键查询状态
        适用：NON_IDEMPOTENT_WRITE（下单、支付、发消息）
        分支：
          - 查到已成功 → 直接返回成功，不重发
          - 查到已失败 → 安全重发
          - 查不到 / 下游不支持查询 → 返回「结果未知」，转异步对账或人工处理
```

### 5.2 为什么必须先查

一个具体的时间线：

```
t0   客户端发出 create_order(key=abc)
t1   服务端收到，扣库存、写订单    ← 副作用已经发生
t2   服务端准备返回响应时网络抖动
t3   客户端超时
     │
     ├─ 直接重发        → 第二笔订单
     └─ 先查 key=abc    → 查到订单已存在 → 返回第一笔的结果
```

「先查」的成本是一次额外的查询调用，代价远小于重复下单。

### 5.3 错误语义要区分「失败」和「未知」

这一点很容易被忽略，但对 Agent 场景特别重要，因为**决定是否重试的是模型**。

如果所有工具超时都返回同一个错误码，模型看到的是「工具失败了」，它会倾向于重试。而系统提示词里通常还会写「工具失败时可以修正参数重试一次」——这会让模型对写操作也发起重试。

正确的做法是让错误码携带语义：

| 错误码 | 含义 | 模型应该做什么 |
|---|---|---|
| `TOOL_TIMEOUT_READ` | 读操作超时，确定无副作用 | 可以重试 |
| `TOOL_TIMEOUT_WRITE_UNKNOWN` | 写操作超时，结果未知 | 不能重试；先调用查询工具确认状态，或告知用户「已提交，结果待确认」 |
| `TOOL_REJECTED` | 服务端明确拒绝，未执行 | 修改参数后可以重试 |

同时需要在系统提示词里明确规则，例如：

```
工具返回 TOOL_TIMEOUT_WRITE_UNKNOWN 时，禁止直接重试同一个写操作。
应先调用对应的查询工具确认状态；或明确告知用户「操作已提交，结果待确认」。
如需重试写操作，必须使用上一次调用返回的同一幂等键。
```

这段提示词是设计方案的一部分，不是可选的文案优化。Agent 系统里，重试决策最终由模型做出，不给它规则它就会按默认行为（重试）处理。

### 5.4 超时控制的实现边界

需要明确一点：**超时控制通常只能做到「放弃等待」，做不到「保证停止」**。

以线程池实现为例，`Future.cancel(true)` 发出的是中断信号：

- 线程如果响应中断（大多数 IO 操作和 `Thread.sleep`），会停止执行
- 线程如果在执行不可中断的操作（CPU 密集循环、`synchronized` 阻塞、native 调用），会继续跑完

这意味着工具可能在框架已经返回超时错误之后，仍然把副作用落地。所以框架不能把「超时」当成「没有执行」来推理——这也是第 5.1 节必须做状态确认的根本原因。

## 6. 完整链路

把上面的机制串起来，一次工具调用的完整流程：

```
1. 模型输出 tool_calls（含 id）
        │
        ▼
2. 框架读取工具的 ToolPolicy
   ├─ READ_ONLY              → 可并行、可自动重试
   ├─ IDEMPOTENT_WRITE       → 串行、带幂等键重试
   └─ NON_IDEMPOTENT_WRITE   → 串行、绝不自动重试、未知走对账
        │
        ▼
3. 发起调用，透传幂等键
   HTTP Header: Idempotency-Key: <call id>
        │
        ▼
4. 下游用去重账本保证只生效一次
   INSERT ... ON CONFLICT DO NOTHING 抢占成功才执行
        │
        ▼
    ┌──────────┬──────────┬─────────────┬──────────────┐
    成功      确定失败    超时/结果未知   429 / 503
    │          │          │               │
    │          │          ▼               ▼
    │          │    按 policy 处置    确认未执行后
    │          │    · 只读 → 重试      可安全重试
    │          │    · 幂等 → 带键重试
    │          │    · 非幂等 → 先查
    │          │          │
    └──────────┴──────────┴───────────────┘
                    │
                    ▼
5. 回灌给模型：区分「成功 / 失败 / 未知」
   + 结构化错误码 + 明确的下一步建议
```

### 6.1 按工具类型分层落地

不需要所有工具都上完整方案，按副作用强度分层：

| 工具类型 | 需要的机制 |
|---|---|
| 只读（计算、检索、查询） | 无。超时直接重试 |
| 幂等写（置状态、覆盖写、删除） | 幂等键 + 下游去重 |
| 非幂等写，可容忍延迟 | 幂等键 + 去重 + 超时返回「未知」+ 异步对账 |
| 非幂等写，金额敏感 | 幂等键 + 去重 + 两阶段提交（prepare/commit）+ 对账 |

两阶段提交的形态：把「预留」和「确认」拆成两个接口。

```
prepare_order(key)  → 生成 PENDING 状态的预订单，无实际副作用，可以随意重试
commit_order(key)   → 真正扣款确认，靠 key 幂等
```

这样超时发生在 prepare 阶段完全无害；发生在 commit 阶段可以用 key 查状态。

## 7. 取舍

| 方案 | 收益 | 代价 | 适用场景 |
|---|---|---|---|
| 仅在框架层拦截重复调用 | 实现成本接近零 | 无法防住真正的重复副作用；参数格式变化即可绕过 | 内部工具、只读为主、有人工兜底 |
| 幂等键 + 下游去重账本 | 语义正确，能安全扛住超时重试 | 下游需要改造；去重表的存储与清理成本；响应需要缓存 | 有资损风险的写操作 |
| 两阶段提交 | 最强，超时几乎无害 | 接口数量翻倍，状态机复杂度上升 | 支付、金额敏感操作 |
| 不对账，直接返回「结果未知」 | 实现最简单，不会出错 | 体验差，需要人工或异步补偿 | 低频、可人工介入的业务 |

选型原则是按副作用强度分层，而不是一刀切。对所有工具都做幂等键加去重表是过度设计——去重表需要存储、需要清理策略、下游需要配合改造，这些成本只有在真正有重复风险的场景才值得付。反过来，对下单、支付这类操作，靠重试碰运气是不能接受的。

**优先保证正确性，但只在真正需要的地方付这个成本。**

## 8. 几个常见疑问

**问：为什么不用分布式锁？**

锁解决的是并发互斥，不是重复请求。超时重试的场景下，第一次请求可能早已结束（锁已释放），第二次请求照样能拿到锁并执行。锁防不住这个场景。幂等键加去重账本才是对症的工具。

**问：下游没有实现去重怎么办？**

可以在框架侧加一层本地去重（key 到结果的映射），但它只能防住同一个进程内的重试，跨进程或进程重启就失效。根本解法仍然是下游去重，因为只有下游知道业务唯一性约束是什么——比如「同一用户同一秒只能下一单」这种规则，框架侧无从判断。

**问：幂等键被复用了怎么办？**

去重表要存请求体摘要（request_hash）。同一个 key 配不同的请求体，必须报错而不是静默执行。这是上游的 bug，静默处理会掩盖问题。

**问：PROCESSING 状态卡死怎么办？**

需要超时回收，或者用业务侧的唯一约束兜底。实践中更稳的做法是两条都上：去重账本作为快速路径拦截明显重复，业务表的唯一索引作为最终保证。只依赖账本的话，账本本身出问题就会导致资损。

**问：读操作的幂等重试会不会有问题？**

读操作没有副作用，重试是安全的，但要考虑成本。对大结果集的查询，重试会消耗成倍资源，所以仍然建议有重试上限和退避。

---

## 9. 小结

围绕这道题的三个层次，结论是：

**能不能重试，由工具的语义决定。** 工具需要用元数据声明自己是只读、幂等写还是非幂等写，框架据此选择执行策略。默认值取最保守的一档，让未声明的工具走安全路径。

**重试怎么不出事，由幂等键和去重账本决定。** 幂等键在调用创建时生成一次，所有重试复用；下游用唯一约束抢占实现「只生效一次」，并缓存响应结果。这里最容易出错的是「重试时重新生成 key」，那样整个机制失效。

**超时之后要不要重试，必须先确认状态。** 超时是「结果未知」而不是「失败」。非幂等写操作必须按幂等键查询状态，查到成功就返回成功，查不到就如实上报不确定，而不是盲目重发。同时错误码要区分「失败」和「未知」，因为 Agent 场景里决定重试的是模型，错误语义会直接影响它的行为。

代价在于下游改造和去重表的维护成本，所以落地时按副作用强度分层，不做过度设计。
