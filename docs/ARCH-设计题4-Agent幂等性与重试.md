# 架构设计题 · 第 4 题：Agent 的幂等性与重试设计

> 作答人视角：这份答案尽量**贴着可运行的系统**讲，而不是罗列概念。
> 凡是涉及「Agent 工具调用」的部分，我都会同时给出本项目（`little-agent`）里已经实现的做法、
> 它的**具体缺陷**、以及生产环境应该怎么补 —— 代码引用都能在本仓库里找到对应行。
>
> 题面：*LLM 输出是非确定性的，工具调用可能超时。重试一次工具调用时，怎么保证不产生副作用（比如重复下单）？
> 如何让 agent 框架感知「这个工具是幂等的」？*

---

## 0. 结论先行

一句话：**幂等性不能靠「重试策略」解决，必须靠「效果账本 + 幂等键 + 工具语义声明」三者合起来解决。**

Retry 只负责「再发一次」，它本身对副作用毫无约束。真正决定安全边界的是三个问题：

| 问题 | 谁负责回答 |
| --- | --- |
| 这次调用**有没有副作用**？ | 工具的**语义声明**（框架感知幂等性的入口） |
| 如果重发，**怎么保证只生效一次**？ | 调用链上传递的**幂等键** + 下游**去重账本** |
| 超时之后**结果到底是成功还是失败**？ | **不能猜**：必须走「查询/对账」，而不是盲目重发 |

后面三节分别展开，第 5 节给出一份可直接落地的设计，第 6 节是取舍与代价。

---

## 1. 先把问题拆对：三类失败，只有一类能靠重试解决

Agent 的一次工具调用，从「模型决定调用」到「效果落地」，中间有多个可能失败的环节。
把它们混在一起谈重试，是设计事故的根源 —— 因为**有些失败重发是安全的，有些重发就是灾难**。

```
模型输出 tool_calls
      │
      ▼
┌─────────────────────────────────────────────────────────────────┐
│ ① 请求根本没发出去 / 没到服务端                                  │
│    网络连不上、DNS 失败、连接被拒                                  │
│    → 确定失败，重发安全 ✅                                         │
├─────────────────────────────────────────────────────────────────┤
│ ② 请求到达了，但服务端明确拒绝                                     │
│    400 参数错、401 鉴权失败、404 路径错                            │
│    → 确定失败，重发无意义（不改参数必再失败）❌                      │
│    → 429 / 503 属于「临时拒绝」：服务端没执行，重发安全 ✅          │
├─────────────────────────────────────────────────────────────────┤
│ ③ 请求到达了，服务端可能已经执行，但客户端没拿到结果                 │
│    ★ 超时、连接中断、502/504（网关超时）                          │
│    → **结果未知**，这才是幂等性问题的主战场 ⚠️                     │
└─────────────────────────────────────────────────────────────────┘
```

### 为什么 ③ 是主战场

以「下单」为例，超时意味着：

```
客户端 ──[创建订单]──▶ 服务端 ──▶ 扣库存 ──▶ 写订单表 ──▶ 发消息
   │                                                      │
   └──── 等待超时，客户端认为失败 ◀───────────────────────┘
                        ▲
                        └── 但订单其实已经创建成功了
```

这时如果框架「重试一次工具调用」，就是**第二笔订单**。

所以第三条硬规则是：

> **超时 ≠ 失败。超时是「状态未知」。对写操作，「状态未知」只能去查，不能重发。**

### LLM 调用本身为什么可以放心重试

对照看一下 LLM 调用 —— 它在同一套分类里属于「重试安全」的典型：

| 特征 | LLM 调用 | 下单工具 |
| --- | --- | --- |
| 是否有副作用 | 无（纯函数：prompt + 参数 → 文本） | 有（改库存、写订单） |
| 重发一次的成本 | 多花一次 token 钱 | 多卖一件货 / 重复扣款 |
| 失败后能否直接重发 | ✅ 可以，最多浪费钱 | ❌ 可能造成资损 |

本项目 `OpenAiCompatibleClient` 的重试逻辑正是建立在这个前提上（`OpenAiCompatibleClient.java:87-123`）：
**网络错误 / 429 / 5xx 重试，401 / 400 / 404 / 422 不重试**。

```java
// OpenAiCompatibleClient.java:114
boolean canRetry = lastError.retryable() && attempt < maxRetries;
```

`retryable()` 的取值就是上面那张分类表的代码化：`LLM_NETWORK_ERROR` / `LLM_RATE_LIMITED` / `LLM_SERVER_ERROR`
为 true，`LLM_AUTH_ERROR` / `LLM_BAD_REQUEST` 为 false（`LlmException.java`）。

**但同一套逻辑套到工具上就危险了** —— 因为工具不再是纯函数。这是整道题的核心分界线。

## 2. 让框架感知幂等性：工具的语义声明

要判断「这个工具能不能自动重试」，框架必须**知道工具的语义**，而不是靠工具名猜。

### 2.1 给工具加一组语义元数据（而不是一个 boolean）

用「是不是幂等」这一个布尔值表达是不够的，因为它回答不了最关键的问题：**失败了该怎么办**。
生产上需要三个正交维度：

```java
public enum Effect {
    /** 只读：不改任何状态。失败随时重试，也可以并行执行 */
    READ_ONLY,
    /** 幂等写：重复执行结果相同（set_x=5 / 覆盖写 / 删除不存在的记录）。可用幂等键安全重试 */
    IDEMPOTENT_WRITE,
    /** 非幂等写：重复执行会产生新效果（下单 / 转账 / 发消息 / 追加记录）。必须带幂等键 + 去重账本 */
    NON_IDEMPOTENT_WRITE
}

public record ToolPolicy(
        Effect effect,
        /** 超时上限；超过就放弃等待（注意：放弃等待 != 副作用没发生） */
        Duration timeout,
        /** 结果未知时的处置策略 */
        UnknownOutcomePolicy onUnknown,
        /** 是否允许框架在同一步内自动重试（默认 false，只有 READ_ONLY 才 true） */
        boolean autoRetry
) {}

public interface Tool {
    String name();
    String description();
    ObjectNode parametersSchema();

    /** 默认最保守：当写操作对待。忘记声明的工具不会因为「没声明」而被自动重试 */
    default ToolPolicy policy() {
        return ToolPolicy.CONSERVATIVE;   // NON_IDEMPOTENT_WRITE + 不自动重试 + 未知就走对账
    }

    ToolResult execute(ObjectNode args, ToolContext ctx) throws Exception;
}
```

### 2.2 三个维度的取值如何驱动框架行为

| `effect` | 可以并行 | 可以自动重试 | 超时后 |
| --- | --- | --- | --- |
| `READ_ONLY` | ✅ | ✅ 最多 N 次 | 直接重试 |
| `IDEMPOTENT_WRITE` | ⚠️ 不建议 | ✅ 带同一个幂等键 | 用同一个键重试，下游保证只生效一次 |
| `NON_IDEMPOTENT_WRITE` | ❌ 必须串行 | ❌ **绝不自动重试** | 走「查状态」；查不到就**返回不确定给用户/人工**，绝不假设失败 |

这张表是整套设计的**决策核心**：框架不需要理解业务，只需要按语义分类执行策略。

### 2.3 本项目的现状与差距（诚实说明）

本项目 `Tool` 接口目前**没有** `policy()`（`Tool.java`）：

```java
public interface Tool {
    String name();
    String description();
    ObjectNode parametersSchema();
    ToolResult execute(ObjectNode args, ToolContext ctx) throws Exception;
}
```

它用一个更弱的替代品：`AgentRuntime` 里按「工具名 + 参数」计数的**重复调用保护**（`AgentRuntime.java:291-299`）：

```java
int count = signatureCounts.merge(call.signature(), 1, Integer::sum);
if (count > config.maxRepeatedToolCalls()) {   // 默认 2
    result = ToolResult.error("REPEATED_CALL", "...重复调用被 Runtime 拦截...");
}
```

**必须说清楚它的三个局限**（这也是我在架构上要改的地方）：

| 局限 | 具体表现 | 后果 |
| --- | --- | --- |
| ① 只是**启发式**，不是幂等性保证 | 它拦的是「模型原地打转」，不是「重复副作用」 | 第一次调用如果已经产生了副作用，拦截第二次并不能撤销第一次 |
| ② 计数是 **per-run** 的 | `signatureCounts` 是 `runLocked` 的局部变量（`AgentRuntime.java:155`） | 跨轮次的重复调用完全不设防 |
| ③ 签名是**参数字符串原文** | `ToolCall.signature()` = `name + "\|" + argumentsJson.strip()`（`ToolCall.java:41-43`） | `{"a":1,"b":2}` 与 `{"b":2,"a":1}` 是两个签名，**换个键序就绕过** |

**结论**：它是个有用的「防跑偏」护栏，但**不能当幂等性机制**。真正的幂等性必须由下面第 3、4 节补齐。

> 面试里这一点值得主动讲：**「我知道我的重复调用保护只是个启发式，它防不住真正的重复副作用 —— 所以我把它和幂等键设计分开对待。」**
> 主动区分「启发式护栏」和「正确性保证」，比假装它很完备要可信得多。

## 3. 幂等键：把 `toolCallId` 变成端到端的去重依据

### 3.1 幂等键从哪来：现成的，就是 `toolCallId`

好消息是：**这个基础设施已经在了**。OpenAI 的 function calling 协议本来就给每次调用一个 id：

```json
{
  "role": "assistant",
  "tool_calls": [{
    "id": "call_00_m5DlyHgCNWbWY7WnBSDA6703",   // ← 这就是天然的幂等键
    "type": "function",
    "function": { "name": "create_order", "arguments": "{...}" }
  }]
}
```

本项目已经把 `call.id()` 贯穿了整条链路：

| 环节 | 代码位置 | 作用 |
| --- | --- | --- |
| 解析出 id | `OpenAiCompatibleClient.java:271` | 从 `tool_calls[].id` 读取 |
| 传给工具 | `ToolContext.callId` | 工具能拿到「我是哪一次调用」 |
| 回灌配对 | `AgentRuntime.java:304` `Message.tool(call.id(), ...)` | 协议要求，否则 API 400 |
| 写入 trace | `Tracer.data("callId", call.id())` | 可观测、可对账 |

**所以不需要发明新东西** —— 只需要把这个 id **继续往下传**，传到真正产生副作用的地方：

```
模型 tool_calls[].id = "call_00_xxx"
        │
        ▼
  AgentRuntime（本项目）── 已透传到 ToolContext.callId
        │
        ▼
  Tool.execute(args, ctx) ── 工具把 ctx.callId() 作为 Idempotency-Key 带给下游
        │
        ▼
  下游服务（订单/支付）── 用这个 key 去重
```

### 3.2 关键细节：幂等键必须**跨重试复用**，不能每次重新生成

这是最容易踩的坑：

| 做法 | 结果 |
| --- | --- |
| 重试时**复用**同一个 `callId` | ✅ 下游能识别为「同一次请求」并去重 |
| 重试时**生成新的 UUID** | ❌ 下游看到两个不同的 key → 认为是两笔独立业务 → 重复下单 |

所以规则是：

> **幂等键在「模型决定调用」的那一刻生成一次，之后所有重试都必须复用它。**
> 绝不能放在 HTTP 客户端或工具实现里「每次请求生成」。

本项目的 `ToolCall.of(...)` 会在缺 id 时生成一个（`ToolCall.java:31-33`），
**这正是要小心的点**：它是「调用对象创建时」生成，所以同一个 `ToolCall` 实例被重试时会复用 ✅；
但如果上层重新构造了一个 `ToolCall`（比如解析两次文本），id 就变了 ⚠️。
生产实现应该把幂等键显式地存在「调用记录」里，而不是依赖对象身份。

### 3.3 下游怎么用这个键去重（去重账本）

幂等键本身不保证任何东西，**必须有一张去重表**来做「只生效一次」：

```sql
-- 去重账本：同一个 idempotency_key 只允许成功一次
CREATE TABLE idempotency_record (
    idempotency_key VARCHAR(64) PRIMARY KEY,
    request_hash    CHAR(64)     NOT NULL,   -- 请求体摘要，防止同 key 不同内容
    status          VARCHAR(16)  NOT NULL,   -- PROCESSING / SUCCEEDED / FAILED
    response_body   TEXT,                    -- 成功时缓存原始响应，供重试直接返回
    created_at      TIMESTAMP    NOT NULL,
    updated_at      TIMESTAMP    NOT NULL
);
```

核心流程（伪代码）：

```python
def handle_with_idempotency(key, request, biz_handler):
    # 1) 抢占：靠主键唯一约束保证并发下只有一个请求能插入成功
    try:
        insert into idempotency_record(key, hash(request), status='PROCESSING', ...)
    except DuplicateKey:
        # 2) 已经有记录了 —— 说明这个 key 来过
        existing = select * from idempotency_record where idempotency_key = key
        if existing.request_hash != hash(request):
            raise Conflict("同一个幂等键被用于不同的请求体")   # 客户端 bug，必须报错

        if existing.status == 'SUCCEEDED':
            return existing.response_body          # 直接返回上次结果，不重复执行 ✅
        if existing.status == 'PROCESSING':
            raise RetryLater("上一次还在处理中")     # 让它稍后查，别并发执行
        if existing.status == 'FAILED':
            # 明确失败过 —— 是否允许重试取决于业务语义
            ...

    # 3) 真正执行业务（注意：执行与记账需要在同一事务，或用 outbox 保证最终一致）
    result = biz_handler(request)

    # 4) 落结果
    update idempotency_record set status='SUCCEEDED', response_body=result where idempotency_key = key
    return result
```

**几个必须注意的点**：

1. **靠数据库唯一约束抢占，不靠「先查再插」** —— 后者在并发下有竞态（两个请求同时查到「不存在」）。
2. **`request_hash` 必须校验** —— 防止同一个 key 被复用到不同请求（那是上游 bug，必须显式报错而不是静默执行）。
3. **`PROCESSING` 状态要能过期** —— 否则进程崩溃后这个 key 永久卡死，需要超时回收（或者干脆用「业务侧唯一约束」兜底）。
4. **响应要缓存** —— 否则重试虽然不会重复执行，但会返回错误的结果给调用方。

## 4. 「超时后结果未知」怎么办：先查，别猜

这是第 3 节的自然延伸，也是整套设计里**最容易被忽略**的一环。

### 4.1 三种处置策略（对应 `UnknownOutcomePolicy`）

```
工具超时了，我们不知道下游执行到哪一步
        │
        ├─▶ 【AT_MOST_ONCE】放弃重试，直接把「结果未知」告诉模型/用户
        │    适用：读操作、幂等且便宜的写
        │    问题：用户体验差（「我不知道有没有成功」）
        │
        ├─▶ 【RETRY_WITH_KEY】用同一个幂等键重发
        │    适用：IDEMPOTENT_WRITE，或下游已实现去重账本
        │    前提：**下游必须真的实现了去重**，否则等于重复下单
        │
        └─▶ 【RECONCILE_FIRST】先查询状态，再决定
             适用：NON_IDEMPOTENT_WRITE（下单/支付/发消息）
             做法：调用「按幂等键查询」接口
                   - 查到成功 → 当作成功返回，不重发
                   - 查到失败/不存在 → 安全重发
                   - 查不到（不支持查询）→ 返回不确定，转人工/异步对账
```

### 4.2 为什么「先查」是必须的：一个真实的时间线

```
t0  客户端发出 create_order(key=abc)
t1  服务端收到，创建订单，扣库存  ← 副作用已经发生
t2  服务端准备返回响应时，网络抖动 / 服务端 GC 停顿
t3  客户端超时（比如 5s）
    │
    ├─ 如果框架直接重发 → 第二笔订单 ❌
    └─ 如果框架先查 query_order(key=abc) → 查到订单已存在 → 直接返回第一笔的结果 ✅
```

### 4.3 本项目的对应实现与缺口

本项目 `ToolInvoker` 超时处理（`ToolInvoker.java:120-124`）：

```java
} catch (TimeoutException e) {
    future.cancel(true);
    return ToolResult.error("TOOL_TIMEOUT", "工具 `" + tool.name() + "` 执行超时（>" + timeoutMs + "ms），已中断。");
}
```

**注意这里的 `future.cancel(true)` 只是「请求中断」，不是「保证停止」**：

- 线程如果响应中断，会停 ✅
- 线程如果在做不可中断的操作（CPU 密集循环、`synchronized` 阻塞、native IO），**会继续跑完** ⚠️
- 也就是说：**工具可能在返回 `TOOL_TIMEOUT` 之后，仍然把副作用落地了**

我在代码注释里明确写了这个边界（`ToolInvoker.java:27-33` 那条防护说明里特别标注「这是**请求**中断」）。
这正好是面试时值得展开的点：

> 「我的超时实现只保证请求中断。对写工具来说，超时之后意味着**结果未知**，
> 框架绝不能假设失败 —— 正确的做法是带着幂等键去查状态。」

### 4.4 给模型的错误信息也要区分「失败」和「未知」

这一点很反直觉但很重要。本项目目前超时统一返回 `TOOL_TIMEOUT`，模型看到会倾向于
「那我重试一次」（系统提示词里也确实写了「修正参数后最多重试一次」）。

**对写工具，这会导致模型主动触发重复副作用。** 正确做法是区分错误语义：

| 错误码 | 语义 | 模型应该做什么 |
| --- | --- | --- |
| `TOOL_TIMEOUT_READ` | 读操作超时，确定没影响 | 可以重试 |
| `TOOL_TIMEOUT_WRITE_UNKNOWN` | **写操作超时，结果未知** | **不要重试**，告诉用户「已提交，正在确认」或调用查询工具 |
| `TOOL_REJECTED` | 服务端明确拒绝，没执行 | 可以修改参数后重试 |

并且要在**系统提示词**里写清楚规则：

```
6. 工具返回 TOOL_TIMEOUT_WRITE_UNKNOWN 时，禁止直接重试同一个写操作。
   应该：① 先调用对应的查询工具确认状态；② 或明确告知用户「操作已提交，结果待确认」。
   重试写操作必须使用工具返回的同一幂等键。
```

**这段提示词是整套设计的一部分**，不是「文案优化」——因为决策者是模型，不给它规则它就会重试。

## 5. 完整设计：一次工具调用的幂等性链路

把前面几节串起来，这是生产环境我建议的结构：

```
┌─────────────────────────────────────────────────────────────────────────┐
│ 1. 模型输出 tool_calls（带 id）                                          │
│    "id": "call_00_xxx"  ← 幂等键的源头                                   │
└────────────────────────────────┬────────────────────────────────────────┘
                                 ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 2. Runtime 查工具语义声明 ToolPolicy                                     │
│    ├─ READ_ONLY              → 可自动重试、可并行                         │
│    ├─ IDEMPOTENT_WRITE       → 带幂等键重试                              │
│    └─ NON_IDEMPOTENT_WRITE   → 绝不自动重试；未知走对账                    │
└────────────────────────────────┬────────────────────────────────────────┘
                                 ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 3. 发起调用：把幂等键透传到下游                                           │
│    HTTP Header: Idempotency-Key: call_00_xxx                            │
│    （或放进业务参数里，取决于下游约定）                                     │
└────────────────────────────────┬────────────────────────────────────────┘
                                 ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 4. 下游用去重账本保证「只生效一次」                                        │
│    INSERT ... ON CONFLICT DO NOTHING  →  抢占成功才执行                    │
└────────────────────────────────┬────────────────────────────────────────┘
                                 ▼
        ┌──────────────┬─────────┴──────────┬──────────────────┐
        ▼              ▼                    ▼                  ▼
   成功返回        确定失败            超时/未知           429/5xx
        │              │                    │                  │
        │              │                    ▼                  ▼
        │              │         ┌──────────────────┐   确认未执行后
        │              │         │ 按 policy 处置：  │   可安全重试
        │              │         │ · 只读 → 重试     │
        │              │         │ · 幂等 → 带键重试 │
        │              │         │ · 非幂等 → 对账   │
        │              │         └──────────────────┘
        │              │                    │
        └──────────────┴────────────────────┴──────────────────┐
                                                                ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 5. 回灌给模型：区分「失败」/「未知」/「成功」                              │
│    + 结构化错误码 + 明确的下一步建议（重试 / 查询 / 放弃）                  │
└─────────────────────────────────────────────────────────────────────────┘
```

### 5.1 三类工具在本项目里的落地示例

| 工具 | 语义声明 | 自动重试 | 超时处置 |
| --- | --- | --- | --- |
| `calculator` | `READ_ONLY` | ✅ 可重试 | 直接重试 |
| `search` / `read_docs` | `READ_ONLY` | ✅ 可重试 | 直接重试 |
| `weather` | `READ_ONLY` | ✅ 可重试 | 直接重试 |
| `todo`（add/done） | `IDEMPOTENT_WRITE`（`done` 幂等；`add` 需要按 item 去重） | ⚠️ 谨慎 | 用 key 重试 |
| 未来的 `create_order` / `send_email` | `NON_IDEMPOTENT_WRITE` | ❌ 绝不 | 先查状态 |

> 有意思的是：本项目现有的 5 个工具**全是读操作或幂等写**（todo 的 add 可以通过 item 去重），
> 所以「不自动重试写工具」这条规则在这里不会造成功能损失 —— 这也是它暂时没暴露这个问题的原因。

### 5.2 除了幂等键，还有两道防线

**① 同一 step 内的工具串行执行（而不是并行）**

本项目 `AgentRuntime.java:209-213` 是顺序 `for` 循环。这带来一个副作用防护：

- 如果模型一步里请求了两个写工具，串行能保证**前面失败时后面还能被拦下**（或至少顺序可见）
- 并行执行时必须额外做「同一资源的写操作互斥」，否则两个写操作并发冲突

**② 写操作的「两阶段」思路（prepare / commit）**

对于特别重要的写操作（支付），更稳的是拆成两步：

```
prepare_order(key)   → 进入 PENDING，返回预订单号（无副作用，可随意重试）
commit_order(key)    → 真正的扣款+确认（幂等，靠 key 去重）
```

这样超时发生在 prepare 阶段完全无害，发生在 commit 阶段可以用 key 查状态。

## 6. 取舍与代价（这部分比方案本身更重要）

任何幂等方案都不是免费的。作为架构决策，必须把代价说清楚：

| 方案 | 收益 | 代价 | 什么场景值得 |
| --- | --- | --- | --- |
| **只在框架层拦截重复调用**（本项目现状） | 实现成本 ~0 | 防不住真正的重复副作用；可被参数键序绕过 | 内网工具、只读为主、可人工兜底 |
| **幂等键 + 下游去重账本** | 语义正确，能扛超时重试 | 下游必须改造；要维护去重表（存储 + TTL 清理）；响应要缓存 | 有资损风险的写操作（下单/支付/转账） |
| **两阶段（prepare/commit）** | 最强，超时几乎无害 | 接口数量翻倍，状态机复杂 | 支付、金额敏感操作 |
| **超时后不对账，直接返回未知给用户** | 实现最简单，绝不出错 | 用户体验差，需要人工/异步补偿 | 低频、可人工介入的业务 |

### 我实际会怎么选

```
按「副作用强度」分层，而不是一刀切：

只读工具        → 直接重试，什么都不用做
幂等写          → 加幂等键，下游加去重表
非幂等写（低频）→ 幂等键 + 超时后返回「不确定」+ 人工/异步对账
非幂等写（高频、金额敏感）→ 幂等键 + 两阶段 + 对账
```

**核心原则：正确性优先于体验，但只在真正需要的地方付这个成本。**
把所有工具都做成幂等键 + 去重表是过度设计；反过来，对下单这种操作「靠重试碰运气」是事故。

## 7. 一句话总结（面试可直接说）

> 「我的 Agent 里工具超时只做了**请求中断**，而且重复调用保护是个按参数字符串计数的**启发式**——
> 它能防模型原地打转，但**不是幂等性保证**，参数换个键序就能绕过。
>
> 真正的幂等要靠三件事：① 工具用 `ToolPolicy` 声明自己是只读 / 幂等写 / 非幂等写，
> 框架据此决定能不能自动重试；② 把模型给的 `toolCall.id` 作为幂等键透传到下游，
> 下游用去重账本保证只生效一次，而且**所有重试必须复用同一个键**；
> ③ 超时之后**不能假设失败**——非幂等写必须先按键查状态，查不到就如实返回『结果未知』，
> 而不是盲目重发。
>
> 这套设计的成本主要落在下游改造和去重表的维护上，所以我会按副作用强度分层：
> 只读直接重试、幂等写加键、非幂等写加键 + 对账，而不是一刀切。」
