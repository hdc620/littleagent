# 上下文工程与记忆（知识库文档 CTX-002）

## 1. 上下文预算

上下文不是越大越好。每一轮请求都要重新计费，且过长的上下文会稀释模型的注意力。
实践中按「估算 token」做预算管理，中文约 1 字 ≈ 0.6 token，英文约 4 字符 ≈ 1 token。

## 2. 三段式上下文

mini-agent 把送给模型的消息分成三层，每次调用 LLM 之前重新组装：

| 层次 | 内容 | 放置位置 | 召回时机 |
| --- | --- | --- | --- |
| 长期记忆 | 历史压缩摘要 | system 消息 | 每轮都注入 |
| 工作记忆 | 待办列表、最近工具结论 | system 消息 | 每轮都注入 |
| 情节记忆 | 与当前问题相关的历史片段 | system 消息（召回块） | 每轮按关键词+时间衰减打分召回 Top-K |
| 短期记忆 | 最近 N 轮原始消息 | 对话消息（保序） | 每轮保留 |

## 3. 压缩策略

当估算 token 超过阈值时，把「最近 N 轮」之外的旧消息交给 LLM 摘要，摘要与已有摘要增量合并。
摘要失败（网络异常/超预算）时必须退化为确定性摘要（抽取用户诉求 + 工具结论），保证循环不中断。

## 4. 常见错误

- 把历史里 assistant 的中间思考原样塞回上下文：既浪费预算，又可能污染后续推理。
- 截断时从中间切断 assistant(tool_calls) 与 tool 消息的配对：会导致 API 400。
  正确做法是按「完整轮次（turn）」切分，并以 user 消息为边界。
